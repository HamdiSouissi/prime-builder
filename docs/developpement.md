# Développement de Prime Builder

Ce document décrit l’implémentation 0.1.0, et non les fonctions encore absentes. Les classes et hooks du CMS cités ici ont été repérés dans le code de Prime CMS 1.0.1 et 1.0.2. Le code du CMS n’est pas modifié par le plugin.

## Structure

- `plugin.json` : manifeste et compatibilité déclarée ; `src/Plugin.php` : enregistrements et cycle de vie.
- `src/Controller/` : tableau de bord, éditeur, API, feuilles CSS.
- `src/Document/` : extraction du bloc, validation, modèles ; `src/Widgets/` : catalogue, rendu, contenu et pont limité vers des blocs Prime.
- `src/Styles/` : compilation autorisée, kit et instantanés CSS ; `views/`, `assets/` et `lang/{fr,en}/` : interface et traductions.
- `templates/` : modèles JSON ; `tests/` : tests PHP, modèle JS et Playwright/axe ; `.github/workflows/ci.yml` : CI.
- `src/Forms/`, `src/Controller/ContactForms.php` et `migrations/` : formulaire fixe, jetons, quotas, envois et purge ; `migrations/README.md` décrit les tables et leur suppression.

## Format et limites

Le document sauvegardé est un document Prime v1 contenant un unique bloc `prime-builder/layout` :

```json
{"version":1,"blocks":[{"id":"pb_layout","type":"prime-builder/layout","data":{"version":1,"elements":[{"id":"intro","type":"heading","settings":{"text":"Bonjour","level":2},"styles":{"desktop":{"color":"#123456"}},"children":[]}]}}]}
```

`Validator` limite les données de mise en page encodées à 1 Mio, 500 éléments et une profondeur de 12 ; les identifiants doivent être uniques et ne contenir que lettres, chiffres, `_` et `-`. Il vérifie le catalogue, les champs, les enfants et les propriétés CSS autorisées. Les métadonnées facultatives `label` (nom de l’élément dans le navigateur) et `hidden` (booléen) sont validées ; un élément masqué conserve son HTML avec l’attribut `hidden`, et ce mécanisme ne protège pas des données confidentielles. Les champs `rich` passent par `Prime\Security\HtmlSanitizer` ; les URL et valeurs CSS ont leurs propres listes de validation. Le `Renderer` échappe les sorties et isole les erreurs de rendu d’un widget.

Le bloc est enregistré avec `PluginContext::blocks()` ; `EntryService::update()` valide et sauvegarde le document, le HTML rendu, le texte et les révisions du CMS. `Converter` tente de convertir les blocs existants sans écrire à l’ouverture : huit types statiques peuvent devenir des widgets `prime_block` si leur rendu normalisé est identique au fragment attribué ; les ancres des titres sont conservées. Les autres blocs peuvent être conservés en lecture seule avec leur HTML authentifié et chiffré, lié à l’entrée et à `APP_KEY`. Si un seul moteur de bloc est indisponible, le fragment est déduit par comparaison des rendus actuels des autres blocs avec le préfixe et le suffixe sauvegardés : cela suppose que ces rendus n’ont pas changé. Le CMS ne conserve pas séparément les fragments ; avec plusieurs moteurs indisponibles ou une comparaison impossible, le HTML sauvegardé entier est conservé dans un unique widget `original_group` non éditable. Le marqueur de groupe est authentifié, l’éditeur signale ses limites à chaque ouverture, et les blocs ne peuvent être séparés dans cet élément. Les réglages d’origine sont perdus à l’enregistrement et la sortie dynamique figée. Un échec de clé, de validation ou de taille continue à bloquer l’enregistrement : le chiffrement peut rendre un HTML inférieur à 1 Mio trop volumineux pour le document. Une modification de `APP_KEY` rend les fragments conservés illisibles. Depuis Prime CMS 1.0.1, `EntryView::content()` détecte les blocs dynamiques par leur type décodé ; le plugin ne modifie plus la représentation JSON des contenus.

Avant de proposer l’édition ou de sauvegarder via l’API Builder, `Converter` vérifie les blocs Builder déjà enregistrés, y compris dans un document mixte, avec l’identifiant de l’entrée. Les fragments étrangers, un groupe mal étiqueté, les widgets indisponibles et les structures non valides sont refusés avant tout repli groupé ; les blocs mal formés que le décodeur du CMS aurait écartés, les racines JSON corrompues ou scalaires et les versions brutes incompatibles sont également signalés. La forme brute distingue un tableau JSON d’un objet de blocs non vide, y compris si les clés de l’objet sont `"0"`, `"1"`, etc. Les formes vides testées (chaîne blanche, `{}`, `[]`, ou blocs vides avec version 1 ou absente, même sous forme d’objet vide) restent utilisables, y compris lorsqu’un HTML séparé doit être conservé. L’avertissement et les contrôles d’enregistrement désactivés sont présents dans le HTML même sans JavaScript ; le `PATCH` Builder retourne 422 même si le client envoie une mise en page vide valide. Une erreur de conversion laisse les données enregistrées intactes. Les contenus et sceaux anciens valides restent éditables, sous réserve des droits habituels ; le client complète en mémoire les champs de nœuds facultatifs absents après validation. Le contrôle ne constitue pas un audit de toutes les corruptions ni une transaction de comparaison et écriture ; `source_hash` reste facultatif et sa vérification n’est pas atomique avec l’enregistrement.

Pour conserver cette protection avec un client périmé, chaque `PATCH` refait la conversion du contenu enregistré avant de valider la demande. Pour une ancienne entrée, cela peut réexécuter les moteurs de blocs et chiffrer son HTML ; le coût et les effets des extensions tierces dépendent du site. Une mesure locale synthétique est consignée dans `RETOUR.md` ; elle n’est pas une garantie de performance en production.

Cette garde ne corrige pas `EntryService::duplicate()` : le noyau crée toujours un brouillon dont les fragments liés à la source ne rendent pas leur HTML. Elle ne protège pas les écritures ou publications effectuées avec le service, l’éditeur ou l’API du noyau, ni les opérations lorsque le plugin est désactivé. Aucun fragment étranger n’est réauthentifié ; conserver les sauvegardes, reconstruire la copie et vérifier son rendu avant publication. Une clé ou un widget disparu peut aussi bloquer un contenu légitime jusqu’à restauration de sa dépendance ou de ses sauvegardes.

## Routes et sécurité

| Route | Usage et contrôle |
|---|---|
| `GET /admin/prime-builder` | Tableau de bord, administration et `prime_builder.edit`. |
| `GET /admin/prime-builder/edit/{id}` | Éditeur plein écran ; capacité du plugin et `EntryService::canEdit()` pour l’entrée et son type. |
| `GET/POST /admin/prime-builder/settings` | Réglages et kit ; `prime_builder.settings`, CSRF du CMS sur l’écriture, validation des valeurs avant enregistrement. |
| `GET/POST /admin/prime-builder/theme` | Sélection de copies statiques pour l’en-tête et le pied de page ; `prime_builder.theme_builder`, CSRF, et `prime_builder.unfiltered_html` si une copie contient le widget HTML. |
| `GET /admin/prime-builder/submissions` ; `POST /admin/prime-builder/submissions/{id}/delete` | Boîte limitée aux 100 derniers messages et suppression ; `prime_builder.forms`, CSRF du CMS sur la suppression, réponses privées `no-store`. |
| `GET /api/prime-builder/v1/forms/{id}/start?node=…` ; `POST /api/prime-builder/v1/forms/{id}/submit` | Routes publiques pour un widget de formulaire visible sur une entrée publique ; jeton temporaire, quotas et validation côté serveur, réponses `no-store`. |
| `PATCH /api/prime-builder/v1/documents/{id}` | Document v1 mono-bloc ; API du CMS, `prime_builder.edit`, contrôle par entrée, CSRF en session, validation du contenu enregistré et de la demande, puis `EntryService::update()`. Une conversion impossible bloque aussi les remplacements valides (422). |
| `POST /api/prime-builder/v1/documents/{id}/render` | Même contrôle ; valide tout l’arbre et retourne l’aperçu HTML sans enregistrer. Le champ facultatif `target` demande le rendu d’un seul sous-arbre existant ; sans lui, la réponse contient aussi le document normalisé. |
| `GET /api/prime-builder/v1/documents/{id}/live` | Retours HTML des widgets de contenu ; entrée publiquement visible ou droits de modification ; `private, no-store`. La pile API du CMS applique sa limite de débit. |
| `GET /prime-builder/css/{id}-{empreinte}.css` | CSS de contenu. Entrée publique ou droit d’édition ; aperçu privé `no-store`. |
| `GET /prime-builder/kit/{empreinte}.css` | CSS du kit global. |
| `GET /prime-builder/theme/{empreinte}.css` | CSS public des parties de thème, adressé par son empreinte et sans texte du modèle. |

Les réglages du plugin ne sont pas enregistrés dans le catalogue générique du CMS : ils passent par une page dédiée, avec leur propre contrôle. Depuis Prime CMS 1.0.2, le catalogue générique applique lui aussi la capacité déclarée pour chaque section. Après validation, l’ensemble est enregistré en un seul réglage JSON `plugin.prime-builder.configuration` ; le noyau émet un seul `settings.updated` pour cette clé. Tant qu’une clé n’est pas présente dans ce groupe, les anciennes valeurs individuelles sont lues en repli. Après un premier enregistrement via la page, modifier directement une ancienne clé individuelle ne remplace pas la valeur présente dans le groupe. L’atomicité porte sur l’écriture SQL du groupe ; les effets externes des écouteurs du CMS et les exceptions qu’ils peuvent lever ne sont pas transactionnels. La bibliothèque (y compris les modèles personnalisés partagés) est lisible par `prime_builder.edit`. Les routes de création, suppression et validation d’import exigent aussi `prime_builder.templates` ; l’import vérifie en outre les droits sur l’entrée. Chaque modèle validé est stocké dans un réglage non autoloadé distinct `plugin.prime-builder.saved_template.<id>`, supprimé à la désinstallation, avec un maximum nominal de 50 modèles et une requête de création limitée à environ 128 Kio. Le contrôle du nombre n’est pas atomique entre deux créations simultanées. Les fragments historiques protégés liés à une entrée ne sont pas stockés dans la bibliothèque partagée. Un client autorisé à modifier un document peut toujours composer lui-même un JSON équivalent : la capacité protège les opérations de la bibliothèque, pas l’expression de toute composition possible.

L’API accepte les modes d’authentification du CMS, notamment une session avec en-tête `X-Prime-CSRF` ou un jeton porteur autorisé. Depuis Prime CMS 1.0.2, le noyau intersecte les capacités d’un jeton avec celles du compte courant et ne traite pas un `*` stocké comme un rôle administrateur. Sur 1.0.1 uniquement, le plugin enregistre dans `Kernel::registerMiddlewareAlias()` un adaptateur de l’alias `api.auth` : il délègue d’abord l’authentification et le CSRF à `ApiAuthenticate`, recharge le compte actif, retire le joker et intersecte les capacités avant les autres middlewares et contrôleurs API. Cela protège les routes HTTP du noyau et du plugin tant que cet adaptateur est effectif ; ce n’est pas une correction du service de jetons lui-même. Le plugin désactivé, en échec ou en mode sans échec, ou une extension qui remplace ultérieurement le même alias, réexpose le défaut du noyau 1.0.1. Les appels directs à `ApiTokenService::authenticate()` ne sont pas corrigés non plus. Mettre le CMS à jour vers 1.0.2 reste vivement recommandé. Le diagnostic système signale ce risque ; les tests et la portée de la CI sont indiqués dans `RETOUR.md`.

Le widget `html` applique toujours `HtmlSanitizer::sanitizeBasic` : son nom de capacité `prime_builder.unfiltered_html` n’autorise ni scripts ni HTML non filtré. La validation et le rendu refiltrent le contenu. Le texte riche ordinaire utilise le même profil ; cette capacité protège le widget et ses opérations, pas toutes les balises permises dans les autres widgets. L’API du constructeur retourne 403 pour une création, modification ou duplication non autorisée, ainsi que pour l’import ou l’enregistrement comme modèle contenant ce widget. Un contenu existant authentifié peut être conservé, déplacé ou supprimé après retrait du droit.

Le validateur `BlockDefinition` ne reçoit ni acteur ni entrée. `HtmlContent` authentifie donc le HTML filtré avec une clé dérivée de `APP_KEY`, l’identifiant du widget et celui de l’entrée : le constructeur ne signe qu’après autorisation ; la validation du noyau refuse les données non signées ou falsifiées et le rendu vérifie l’entrée. Les signatures ne sont pas conservées dans les modèles partagés ; une personne autorisée les recrée lors de l’enregistrement. La rotation d’`APP_KEY` invalide les signatures et peut empêcher les sauvegardes ou rendus ultérieurs : sauvegarder la clé et les contenus avant toute rotation.

Le filtre `content.saving` protège également les enregistrements par le service du noyau, sans modifier celui-ci. Comme `Hooks` isole les exceptions des plugins, ce filtre ne peut pas refuser l’opération par une exception : si un acteur sans droit rejoue un ancien widget signé, il restitue le contenu précédent, mais **l’API du noyau peut répondre 200 et les autres champs peuvent être modifiés**. Le constructeur, lui, répond 403 avant la sauvegarde. Lors d’une création ou duplication par le noyau, l’ID de destination n’existe pas encore : les widgets HTML signés sont convertis en texte riche filtré pour conserver leur contenu, sans conserver leur type. Un acteur autorisé qui copie un widget signé vers une entrée existante par l’API du noyau le fait signer pour l’entrée cible. L’autosauvegarde du noyau ne passe pas par ce filtre, mais la restauration passe par `update`. Ces limites et les tests observés sont consignés dans `RETOUR.md`.

Le premier sous-ensemble du Theme Builder utilise `site.partial` pour `header` et `footer` quand le thème appelle ce hook. Le formulaire valide des modèles partagés, puis en stocke une copie indépendante dans `plugin.prime-builder.theme_partials` : un gestionnaire de bibliothèque ne peut pas changer la copie active en supprimant le modèle source. Un filtre antérieur qui a déjà produit une chaîne conserve la priorité. `Partials` revalide les copies, refuse les widgets de contenu dépendant d’une entrée ou d’une route qui ne disposent pas d’un contexte adapté ainsi que le formulaire de contact et les ancres explicites en double, applique les exclusions par identifiant et espace de noms les identifiants et ancres pour chaque partie. L’identité du site, les six widgets de métadonnées d’entrée, le contenu de l’entrée, le fil d’Ariane, le menu de navigation, les boutons de partage, le formulaire de recherche et les widgets d’archive sont autorisés : ils sont calculés côté serveur pour la partie. Les liens des widgets vers ces ancres sont réécrits, pas les liens dans les champs HTML riche. La configuration déclenche `settings.updated` et la purge du cache de pages. Les CSS sont compilés et conservés sous `theme-<empreinte>.css` ; les scripts des widgets présents sont enregistrés depuis `site.assets`. Les modèles de contenu, archives, recherche et 404, conditions par type ou terme et priorités ne sont pas implémentés.

Le formulaire de contact est un premier sous-ensemble fixe, sans upload ni e-mail. `forms.js` demande un jeton à `start` avec `credentials: 'omit'`, puis envoie du JSON sans cookie. Le jeton HMAC, dérivé de `APP_KEY`, lie contenu, nœud, IP, nonce et horodatage ; le serveur impose 3–1 800 secondes et vérifie que le nœud et ses parents ne sont pas masqués dans une entrée publique. À `start` et à `submit`, il vérifie aussi les ancêtres de page : un parent non public, futur, manquant, cyclique ou au-delà de la limite de profondeur rend l’envoi indisponible même pour un jeton déjà émis. Les quotas sont de 30 démarrages par minute et 5 soumissions par 5 minutes pour chaque IP ; si une autre requête crée simultanément le compteur, un nouvel `UPDATE` borné départage la place disponible sans augmenter le plafond. Après un véritable `429`, l’interface signale la limite mais ne réessaie pas automatiquement ; le visiteur doit attendre puis recharger. Le pot de miel est ignoré silencieusement. Les empreintes de jetons utilisés sont insérées sous contrainte unique dans une transaction avec le message, puis conservées séparément pendant au moins la durée de validité maximale. Supprimer un message ne réactive pas son jeton. Les champs sont strictement validés et l’affichage admin échappé. Les compteurs utilisent des clés HMAC plutôt que des adresses en clair ; la résolution de l’IP dépend de la configuration de confiance proxy du CMS. Les tables, la purge après 30 jours et la désinstallation sont décrites dans `migrations/README.md`. Aucun mécanisme n’élimine tout spam et les contrôles de charge, conservation des sauvegardes et obligations de confidentialité restent à la charge de l’opérateur.

L’avis est un contenu éditorial statique : la note est bornée à 0–5 et les étoiles décoratives ont une étiquette textuelle localisée. Il n’émet pas de données structurées de notation ni ne vérifie l’authenticité des avis. La boîte retournable enregistre les deux faces et son lien en HTML lisible ; `flip_box.js` ajoute un bouton natif avec `aria-expanded` et un identifiant de panneau sans collision. Le focus est restitué si le verso contenant le focus est masqué. L’animation déclenchée par l’utilisateur respecte `prefers-reduced-motion` ; sans script, aucun contenu n’est masqué.

Pour Galerie et Carrousel d’images, le sélecteur multiple du CMS ajoute les médias après les lignes `URL|texte alternatif` déjà présentes. L’éditeur refuse atomiquement une sélection dépassant 20 lignes ou 10 000 octets, un texte alternatif de plus de 300 octets, une URL incompatible avec le format ou une ligne vide déjà présente ; les retours à la ligne des textes alternatifs sont remplacés par des espaces. L’ajout normalise les fins de ligne existantes en `\n` et retire les espaces en fin de liste ; il ne préserve donc pas la valeur octet pour octet. La validation PHP reste l’autorité pour les URL et les tailles et normalise les lignes avant sauvegarde. Les textes alternatifs sont des copies, pas des références dynamiques ; les dimensions ne sont pas déduites. La détection d’usages des médias garde les limites décrites dans le README. Le sélecteur natif filtre les images et ne remplace pas l’édition de la liste à la main.

Le portfolio accepte au plus 24 cartes saisies manuellement et 12 catégories, avec titre et catégorie obligatoires ; texte échappé et URL filtrées. `portfolio.js` crée des boutons natifs `aria-pressed` et une annonce du nombre de cartes, sans masquer le contenu si JavaScript est indisponible. Il n’interroge pas les contenus du CMS.

Le formulaire de recherche utilise `UrlGenerator::searchUrl()`. Dans une entrée, `content.js` actualise son action sans remplacer le champ ni sa saisie ; sans JavaScript, l’adresse enregistrée peut devenir périmée. Dans une partie de thème, l’action est générée à chaque rendu serveur, sans script propre ; les identifiants des éléments sont préfixés par partie pour associer chaque libellé à son champ sans collision. Le cache de pages reste activable : le noyau purge toutes ses pages lorsque `permalinks.search_base` est modifié ou supprimé via le service de réglages. Un cache externe ou un changement direct en base ne sont pas couverts.

Le menu de navigation utilise `MenuRepository::all()` pour le sélecteur et `MenuRenderer::renderLocation()` pour les liens, leur hiérarchie et `aria-current`. Le noyau ne vérifie pas tous les ancêtres ni la visibilité des taxonomies et types : pour ce widget uniquement, un filtre temporaire `site.menu_items`, identifié dans les options du rendu et retiré dans `finally`, revérifie les cibles typées après les filtres du noyau et des extensions. Les entrées doivent être publiées et de type public ; les pages doivent avoir au plus 11 ancêtres publics, existants et non cycliques. Les termes et archives exigent une taxonomie ou un type public. Si la page d’articles configurée n’est pas publique, l’archive d’articles utilise `/blog`. Les cibles typées sont relues par lots et leurs URL sont recalculées ; en cas d’échec, seul le repli d’accueil est rendu. Les URL saisies manuellement, y compris les liens non typés ajoutés par des extensions, ne peuvent pas être reliées automatiquement à un contenu privé : leur publication relève de l’administrateur ou de l’extension. Ces vérifications ne changent ni les menus ni les API du noyau en dehors de ce widget.

Dans une entrée, le document stocke un identifiant de menu et un repli vers l’accueil, jamais une copie des titres ; `content.js` demande le menu actuel à l’API et attend que le focus quitte le repli avant de le remplacer. Sans JavaScript ou si l’API échoue, seul le lien d’accueil est disponible. Dans une partie de thème, le menu est recalculé côté serveur avec le chemin réel de `PageContext` ; sans JavaScript tous ses liens et sous-menus restent visibles, et le même script les améliore avec des boutons de divulgation et des ID sans collision. Un menu manquant rend le repli d’accueil. Le cache de pages du CMS est contourné sur tout le site tant qu’une partie contient ce widget : `MenuRepository` n’émet pas d’événement couvrant ses modifications. Les caches externes ne sont pas invalidés. Le point de rupture mobile est lu dans les réglages du constructeur et borné avec la même règle que le point tablette (767 px par défaut). `Compiler` émet les règles responsives par identifiant de widget ; le rendu fournit la même valeur bornée à `content.js` pour `matchMedia`. Une modification des réglages demande la purge du cache de pages du CMS et renouvelle l’empreinte de la feuille ; si le stockage du cache est indisponible, une purge manuelle peut être nécessaire. Si le focus se trouve dans le menu lors d’un redimensionnement, il reste visible ou revient au premier lien. Le bouton mobile utilise `hidden` : il reste disponible même si la feuille de mise en page générée ne se charge pas, mais la présentation peut alors différer. Sans JavaScript, les liens fournis par le serveur restent visibles et suivent aussi la feuille responsive ; dans une entrée, seul le repli d’accueil est disponible.

Le fil d’Ariane utilise `SeoManager::breadcrumbs()`. Dans une entrée, son contexte est reconstitué depuis l’entrée et les URL du CMS : il ne reflète pas les routes personnalisées dont le contexte réel diffère. Dans une partie de thème, le `PageContext` réel fournit entrée, blog, archive publique, terme public, auteur actif ou recherche ; accueil et contextes non pris en charge donnent un fil vide. Les libellés du noyau sont actuellement codés en français. Pour une page, les parents sont relus et ajoutés dans l’ordre ; un parent non public, manquant, cyclique ou plus de 11 ancêtres rend le fil vide. Le générateur d’URL du noyau est amorcé avec les valeurs vérifiées pour ne pas réutiliser un ancien slug dans la même requête. Pour un article, une page d’articles ou un de ses ancêtres non public est remplacé par le lien `/blog`. Le HTML enregistré d’une entrée ne garde que le lien d’accueil, sans titre ni chemin privé ; `content.js` demande la version actuelle à l’API `no-store` et attend que le focus quitte le repli avant de le remplacer. Sans JavaScript ou en cas d’erreur, seul ce repli est visible dans une entrée. Dans une partie, le fil et sa feuille sont servis côté serveur sans script propre ; le cache de pages du CMS est contourné tant qu’une partie contient le widget. L’endpoint live du constructeur vérifie aussi les ancêtres avant de livrer anonymement les données de tous les widgets : une personne autorisée à modifier l’entrée conserve l’accès à son aperçu. Cela ne modifie pas l’API de lecture du CMS : `ContentController::isReadable()` accepte une entrée de statut publié sans vérifier les ancêtres. Ne pas utiliser le statut privé d’un parent comme protection globale des données d’un enfant publié.

Le titre et le logo du site utilisent `SiteView` et les services du CMS : options du thème actif et de son parent, puis réglages du site. Le logo emploie les variantes du média image et le nom du site comme texte alternatif ; si le média manque ou n’est pas une image, le nom échappé est affiché. Le lien vers l’accueil est facultatif et le titre peut être un paragraphe ou une balise `h1`–`h6`. Dans les entrées, le HTML sauvegardé est un repli : `content.js` récupère l’identité actuelle via la route live et diffère le remplacement tant que le focus se trouve dans le widget ; sans JavaScript ou en cas d’échec de la route, ce repli peut être périmé. Les parties de thème recalculent l’identité côté serveur. Le noyau purge les pages après changement de réglages ; le plugin les purge après modification ou suppression de média lorsqu’une partie enregistrée contient un logo. Il s’agit d’une purge globale, pas d’un suivi fin des dépendances médias.

Les quatre widgets de contenu courant (`entry_title`, `entry_excerpt`, `entry_featured_image`, `entry_info`) utilisent `EntryViewFactory` et les valeurs échappées de `EntryView`, avec un seul chargement des relations par instance d’entrée. La route live recharge l’entrée et est `no-store` ; `content.js` attend que le focus quitte chaque widget avant de remplacer son HTML. Le CMS calcule `content_html` avec l’ancienne entrée avant sa mise à jour : pour ne pas publier le titre, l’extrait, l’image ou les informations d’un ancien brouillon lors d’une publication simultanée, le repli est vide si l’ancienne entrée n’est pas publique. Pour une entrée déjà publique, le repli peut rester périmé après modification. Les noms et liens de catégories et les noms d’auteurs ne sont jamais enregistrés : ils ne sont rendus en live que si la taxonomie `category` est publique ou si le compte est actif ; un lien auteur n’est rendu que lorsque le slug résout le bon compte. Sans JavaScript ou si l’API échoue, catégories et auteurs sont donc absents et les autres informations peuvent être anciennes ou vides. Le texte de repli de l’extrait vient du `content_text` du CMS ; l’extracteur du bloc Builder n’a pas d’entrée et n’inclut pas le widget d’extrait lui-même. L’ancien widget `current_content` est lui aussi vide dans le repli pour une entrée non publique, et son auteur n’est jamais conservé dans le HTML enregistré. Dans les parties de thème, ces widgets sont rendus directement à partir du `PageContext`, sans endpoint ni script : le contexte doit être une entrée, un accueil ou un blog sans redirection, avec statut HTTP 200, type et entrée publics, et ancêtres de pages publics et accessibles. Les catégories publiques sont alors disponibles sans JS. Le cache de pages est contourné pour tout le site tant qu’une partie contient un widget d’entrée ou d’archive, car les hooks du noyau ne couvrent pas toutes leurs dépendances. Les données contextuelles ne sont pas copiées dans le modèle enregistré.

La navigation entre contenus utilise `EntryView::previous()` / `next()` du noyau et vérifie les ancêtres des pages, avec un maximum de dix candidats inaccessibles sautés dans chaque direction ; le noyau limite lui-même ses recherches aux dix entrées voisines. La boîte auteur utilise la vue hydratée et le média du CMS, mais n’affiche que les comptes actifs et ne lie une archive que si son slug résout bien le même compte. Dans les deux cas, aucun titre voisin ni profil n’est enregistré dans `content_html` : une entrée ou un compte peut être retiré sans nouvelle sauvegarde du document. Dans une entrée Builder, ces widgets sont donc vides sans JavaScript ou en cas d’échec de la route live ; dans une partie de thème ils sont calculés côté serveur selon le `PageContext` public, sans JavaScript ni persistance. Les contrôles sont des liens natifs ; le rafraîchissement en entrée attend la sortie du focus. Une route personnalisée ou un conflit avec une route réservée du CMS peut encore rendre un lien inaccessible.

`entry_content` lit `EntryView::content()` uniquement dans une partie et un contexte public compatibles ; un garde par identifiant d’entrée empêche une réentrée lors de l’évaluation d’un bloc dynamique. Dans l’entrée enregistrée il est vide et l’éditeur affiche une explication. `ContentFragment` utilise `DOMDocument` et un préfixe aléatoire par copie pour réécrire les ID, les références HTML/ARIA, fragments locaux, noms de cartes d’image et certaines références SVG. Les `data-pb-id` sont volontairement conservés : le CSS compilé et l’API live du document restent applicables aux copies. `content.js` utilise aussi la portée de la copie lors de l’insertion ultérieure d’une zone et réécrit ses références locales. Le test navigateur couvre deux copies dans chaque partie et l’original, les styles, onglets, carrousels, formulaire, zones et absence de JS ; il vérifie aussi SVG, carte d’image, média et suppression de script dans le HTML libre d’une entrée Prime. Pour tester ces références dans une zone actualisée, un fragment est ajouté à une réponse live réelle interceptée ; cela ne constitue pas un test d’une extension tierce.

À l’insertion d’une zone actualisée, `content.js` construit un fragment dans un `<template>`, préfixe les ID et les noms de cartes d’image, puis réécrit les références HTML/ARIA, fragments et attributs SVG pris en charge ; ce n’est pas un assainissement du HTML fourni par le CMS. Il vérifie les cibles générées contre les ID et noms de cartes déjà présents dans le document, ainsi que contre les cibles déjà créées dans le fragment. En cas de doublon dans la zone d’origine, les références pointent vers la première cible. Cette vérification ne contrôle pas les éléments ajoutés ultérieurement par d’autres scripts. Le test navigateur enregistre une vraie zone du noyau avec un bloc HTML autorisé, l’affiche dans la barre latérale et deux widgets d’une entrée, et vérifie une collision d’ID et une collision de nom de carte préexistantes, sans intercepter l’API.

Le rendu Builder récent marque chaque élément d’une empreinte `data-pb-owner` calculée à partir des identifiants, de la structure et des réglages influant sur la CSS, sans le contenu ; ce n’est ni un secret ni un contrôle d’accès. Le compilateur utilise cette empreinte avec une spécificité nulle et ne force pas la typographie à travers un autre `.pb-layout`. Les anciens HTML d’entrée sans marqueur conservent un sélecteur de compatibilité qui exclut les éléments marqués et les éléments non marqués dans un widget de zone ; deux anciens documents non marqués peuvent encore se cibler mutuellement. Le CMS rend à nouveau les zones via `ZoneRepository::renderLive()` dans le thème et le widget ; leurs nouveaux éléments sont donc marqués même si la zone a été sauvegardée avant cette version. Un thème qui affiche directement l’ancien `content_html` d’une zone ne bénéficie pas de cette garantie.

Après le premier rendu complet, l’éditeur marque son canevas dans l’iframe et limite la recherche des éléments, les remplacements ciblés, les actions et les styles aux nœuds de ce document, sans traverser les `.pb-layout` imbriqués. Un clic dans un document copié sélectionne le widget de zone contenant ce document. Le rendu ciblé calcule l’empreinte de style d’après le document complet validé et l’éditeur synchronise les nœuds du canevas avec cette empreinte si un style change ; les documents imbriqués restent distincts. Les feuilles enregistrées restent chargées pour les autres documents et les copies de l’entrée : la nouvelle empreinte empêche les règles récentes du document sauvegardé de s’appliquer au canevas modifié. Une feuille ancienne sans garde, conservée par un cache ou introduite par le thème, peut encore interférer. Si aucun emplacement sûr n’est trouvé, l’éditeur ne désactive pas de feuille ni n’ajoute ses feuilles d’aperçu. L’écouteur de l’iframe est également attaché si celle-ci a déjà terminé son chargement avant le module de l’éditeur.

Pour localiser initialement le contenu, un thème peut marquer son enveloppe unique avec `data-pb-editor-content` ; celle-ci est prioritaire et sera entièrement remplacée dans l’aperçu. Sinon, le rendu récent d’une entrée porte `data-pb-document` avec son ID ; un ancien rendu doté de `data-pb-live` peut aussi être identifié. Les copies `data-pb-content-copy` et les layouts imbriqués sont exclues de cette recherche. Les marqueurs et les enveloppes `.aurora-prose` doivent être cohérents ; si plusieurs candidats restent ambigus, l’éditeur affiche un avertissement plutôt que de remplacer un en-tête ou tout `main`. Le marqueur n’est pas une autorisation et un thème mal configuré peut désigner le mauvais contenu. Un ancien HTML sans marqueur ni URL live, hors Aurora et sans enveloppe explicite, n’a pas d’aperçu actualisé ; l’enregistrement reste possible et doit être vérifié. Les tests utilisent Aurora et une simulation de thème générique par interception, pas tous les thèmes existants. L’aperçu applique ses propres styles en ligne et ne garantit pas l’initialisation interactive de tous les widgets.

`site.assets` compile la CSS de chaque bloc Builder dans les zones enregistrées et déclarées par le thème actif, même sans entrée ou widget de zone ; les feuilles identiques sont dédupliquées, archivées par empreinte et servies par la route de CSS des parties de thème. La route peut recompiler les zones actuelles si l’instantané manque. Les types de widgets sont aussi collectés récursivement pour enregistrer leurs feuilles et scripts déclarés une seule fois. La CSP ajoute l’origine exacte d’OpenStreetMap si une carte est présente, sauf si `frame-src` interdit toute iframe. Le noyau ne communique pas à l’avance les zones effectivement affichées : feuilles, scripts et autorisation CSP peuvent donc concerner une zone non affichée. La CSS ne révèle pas le texte des widgets mais ses identifiants et styles. L’héritage CSS naturel, les règles du thème, les feuilles externes et les anciens documents non marqués restent actifs.

Après insertion d’une copie live, `content.js` émet l’événement bouillonnant `prime-builder:fragment` sur la zone. Les scripts fournis pour les onglets, cartes, comptes à rebours, boîtes retournables, galeries, carrousels d’images, portfolios, vidéos, formulaires et partage initialisent les éléments concernés de façon idempotente ; la navigation utilise aussi cet événement. Les scripts tiers doivent prendre eux-mêmes en charge les insertions tardives. Le CMS rend toutefois les zones avec une entrée nulle : le formulaire de contact est désactivé et plusieurs widgets dépendant de l’entrée courante restent incomplets. Lorsqu’un widget Zone d’une entrée demande sa copie live, `Content::themeZone()` fournit temporairement l’entrée uniquement aux boutons de partage ; un `finally` restaure le contexte même en cas d’erreur. Leurs liens partent du permalien de l’entrée, puis `share_buttons.js` les actualise depuis la canonique publique. Une zone rendue directement par le thème n’a pas ce contexte et son partage reste indisponible. Les tests couvrent une zone native et deux copies, les collisions d’ID des onglets, des interactions au clavier et des notifications répétées ; ils ne garantissent pas tous les widgets, extensions ou thèmes.

Les sauvegardes de zones du noyau observé n’émettent pas de notification de purge du cache de pages. Le filtre `cache.page.cacheable` interroge donc les zones déclarées du thème actif avant toute lecture ou écriture et refuse le cache intégré dès qu’une de ces zones possède un enregistrement, y compris une zone native ou vidée ; il refuse également le cache si cette vérification échoue. Cela évite de ressusciter une page créée avant une modification, mais désactive durablement le cache de pages sur tout le site tant qu’un tel enregistrement existe, avec un coût de performance significatif. Les enregistrements de zones non déclarées ou d’autres thèmes ne déclenchent pas ce contournement ; une activation de thème purge les pages via le noyau. Un thème ou une extension qui affiche une zone non déclarée échappe donc à cette protection. L’activation et la désactivation de Prime Builder purgent explicitement le cache intégré, indépendamment de l’avis de bienvenue ; une requête concurrente peut néanmoins terminer après cette purge. Les caches externes et les feuilles déjà stockées par un navigateur ne sont pas invalidés.

Le traitement `ContentFragment` des copies d’entrée n’est ni un assainisseur ni un parseur HTML5 complet. Les scripts présents dans la copie sont supprimés ; les attributs, CSS intégrés et scripts tiers ne sont pas réécrits s’ils font référence à d’anciens ID. Les actifs déclarés par les widgets Builder de l’entrée et par les blocs Builder des zones déclarées sont enregistrés par `site.assets`, mais ceux injectés par d’autres blocs dynamiques ou extensions ne sont pas garantis. La copie est vide au-delà de 2 Mio ou si libxml détecte une sortie de l’enveloppe ; les structures modernes, les sélecteurs CSS par ID, les ancres nommées et d’autres références non prises en charge peuvent changer ou ne plus fonctionner. Comme pour les autres widgets contextuels des parties, le cache de pages CMS est contourné globalement tant que le widget y figure ; les caches externes ne sont pas contrôlés.

Le titre et la liste d’archive reçoivent le `PageContext` réel du filtre `site.partial`. Ils exploitent ses entrées et sa pagination, sans seconde requête de recherche : 50 entrées au maximum (le plafond du réglage de lecture du CMS). Les types et taxonomies non publics, dates futures, auteurs inactifs, pages aux ancêtres privés ou cycliques et contextes d’erreur sont écartés ; les ancêtres sont chargés par lots. Le total du CMS n’est pas recalculé après ce filtrage : une page peut donc contenir moins de résultats, voire être vide. Les liens de pagination conservent le seul paramètre public `q` pour la recherche. La CSS est déclarée par widget, aucun script n’est nécessaire. Lorsqu’un de ces widgets figure dans un instantané de partie de thème, le filtre `cache.page.cacheable` désactive le cache de pages du CMS pour tout le site ; il ne contrôle pas un cache externe ou CDN. Le contenu enregistré d’une entrée n’a pas accès au `PageContext`, ne conserve aucune donnée d’archive et affiche seulement une explication en aperçu. Ceci n’implémente pas les modèles d’archive du Theme Builder ; un thème qui ne rend pas les parties `header` ou `footer` ne peut pas afficher ces widgets par ce mécanisme.

Les boutons de partage construisent des liens ordinaires vers Facebook, LinkedIn, X et `mailto`, sans SDK tiers. L’URL doit être HTTP(S), sans identifiants ; paramètres et fragment sont retirés, les valeurs encodées, les caractères de contrôle supprimés et `rel="noreferrer"` évite de transmettre le référent. Dans une entrée, l’URL absolue enregistrée provient de `UrlGenerator` ; `share_buttons.js` lit la première balise `link[rel~="canonical"]` de l’en-tête, que `SeoManager::renderHeadTags()` émet d’après le contexte réel et les éventuels filtres `seo.meta`. La canonique est acceptée seulement si elle est absolue, HTTP(S), sans identifiants ni caractères de contrôle ; sinon le script utilise l’origine et le chemin du navigateur. Paramètres et fragment sont toujours retirés. Les aperçus d’administration, `preview=1` ou `preview=true` et `customizer_preview=1` conservent le repli enregistré. Pour un brouillon, ce repli est l’adresse publique prévue et non le lien d’aperçu : elle peut être inaccessible ou périmée. Sans JavaScript, le repli ne suit pas la canonique personnalisée et peut rester périmé après un changement d’adresse. Une balise canonique fournie par un thème ou une extension est utilisée si elle satisfait les mêmes contrôles ; une balise absente, modifiée après le chargement, ou un cache externe périmé peuvent donner un résultat différent.

Dans une partie de thème, `SeoManager::canonicalUrl()` reçoit le `PageContext` réel ; la canonique personnalisée d’une entrée est donc utilisée, mais ses paramètres et son fragment sont retirés. Ce calcul ne reprend pas d’éventuels filtres ultérieurs `seo.meta`. Les liens sont absents si l’URL est invalide, si le contexte est en aperçu, en erreur ou non pris en charge, ou si l’entrée ou l’un de ses ancêtres n’est pas public. Les parties n’émettent pas l’attribut d’actualisation et ne chargent pas le script de partage : même si une entrée de la page le charge, il ne modifie pas leurs liens. Le cache de pages du CMS est contourné pour tout le site tant qu’une partie contient ce widget, afin d’éviter des canoniques périmées après modification d’une dépendance ; les caches externes ne sont pas invalidés.

Le sommaire est calculé au rendu serveur à partir des widgets Titre, Titre animé et blocs Prime de type titre du même document. Il ajoute les titres simples des widgets Carte, Boîte icône, Boîte image, formulaire fixe, Appel à l’action, Table et Liste de prix, Avis et Compte à rebours : ce dernier ne figure que si son échéance valide produit réellement un titre. Les éléments masqués dans Structure, y compris leurs descendants, sont exclus ; une visibilité responsive gérée seulement par CSS ne retire pas l’élément de la liste. Le sommaire produit des listes imbriquées, des cibles stables dérivées des identifiants des widgets et évite les ancres Builder explicites et celles des blocs Prime. Les cibles sont focalisables au clavier sans script. Si un sommaire est présent, l’éditeur réconcilie l’aperçu complet après toute modification pour qu’il suive les titres. Les titres issus du texte riche, du HTML libre, des autres widgets, du thème ou de contenus live ne sont pas tous recensés ; des ID fournis hors du constructeur peuvent entrer en collision. Le HTML enregistré d’une entrée ne change qu’après une nouvelle sauvegarde. Dans une partie de thème, le périmètre reste celui de cette partie, pas celui de la page entière.

Le carrousel de témoignages valide au plus 20 lignes textuelles (auteur, fonction et portrait facultatifs). Les portraits redondants ont un texte alternatif vide ; les URL passent par le filtre de ressources du CMS. Le carrousel de médias valide au plus 20 lignes d’images ou de fichiers vidéo natifs, avec alternative, légende, piste WebVTT et transcription selon le type ; ses textes sont échappés au rendu et ses URL filtrées. Le diaporama valide également 20 lignes au plus : image, alternative, titre, description et lien facultatif dont l’URL et le libellé sont fournis ensemble. Son texte est échappé, ses URL sont filtrées et le niveau de titre est borné à 2–6. Les trois partagent `image_carousel.js` avec le carrousel d’images : les ressources sont dédupliquées, aucun défilement automatique n’est lancé et toutes les diapositives restent présentes sans script. Une vidéo masquée est mise en pause ; ses propres touches ne sont pas interceptées. La CSP du CMS bloque par défaut les ressources distantes, et les pistes WebVTT externes exigent une configuration CORS adaptée.

Le titre animé conserve un seul titre sémantique lisible ; ses deux effets CSS sont désactivés par `prefers-reduced-motion`. Le champ typé `code` préserve le texte et ses espaces (maximum 20 000 octets, octet nul refusé) : il n’est **pas** un HTML assaini et tout rendu d’une extension utilisant ce type doit l’échapper. `CodeHighlighter` échappe chaque fragment, ne génère que ses classes fixes et colore au maximum 1 000 unités ; c’est un colorateur léger et non un parseur complet. Le contenu restant est affiché sans coloration et le conteneur défilant est accessible au clavier.

Le compte à rebours stocke une date à la minute sans fuseau au format `AAAA-MM-JJTHH:MM`, interprétée explicitement en UTC ; le validateur refuse les dates impossibles et les années hors 0001–9999. Le HTML enregistré contient un `<time>` UTC lisible sans script. `countdown.js`, chargé seulement pour ce widget, compare l’échéance à `Date.now()` sur le navigateur et partage un seul intervalle entre les comptes ; un retour de visibilité recalcule le temps absolu. Les valeurs ne forment pas une région live, seul le message de fin est annoncé par `role="status"`. L’horloge locale peut être fausse ; ni le décompte ni son message ne sont un contrôle d’accès côté serveur. Sans JavaScript ou dans l’aperçu statique, seule la date est affichée.

La route `live` vérifie que l’entrée est publique ou que le demandeur peut la modifier ; un éditeur autorisé peut donc aussi prévisualiser son brouillon. Pour les listes d’articles, `EntryQuery` filtre les contenus publics, le type, les termes et l’auteur, puis applique tri, limite et pagination. Les widgets de configuration de requête identique partagent les résultats dans le fournisseur ; les configurations différentes nécessitent chacune leur propre requête. Sans pagination, le fournisseur lit jusqu’à 12 résultats en une requête ; avec pagination, il faut un comptage et une sélection. Pour les pages, les ancêtres absents sont chargés par lots, une requête par niveau (au plus 11), puis transmis à `UrlGenerator::primePageCache()` : on n’effectue pas une requête par résultat. Les pages orphelines, cycliques, trop profondes ou dont un ancêtre est privé sont écartées après la requête ; le comptage de pagination du noyau peut donc inclure ces pages inaccessibles et une page affichée peut être vide. Les tests d’intégration comptent les requêtes du fournisseur sur un et douze résultats, y compris des parents et grands-parents distincts, avec un nouveau générateur d’URL pour chaque mesure et des permaliens en mémoire ; ces nombres ne comprennent pas les requêtes HTTP, d’authentification ou de lecture des réglages. Le navigateur actualise les widgets concernés une fois par document ; seuls leurs paramètres de pagination bornés sont transmis à l’API, pas les autres paramètres de la page. Le HTML de repli ne contient pas de copie persistante des titres d’autres contenus.

À la conversion, `MediaUsageRepository::extractMediaIdsFromDocument()` relève les références que le noyau sait déjà extraire de chaque bloc d’origine ; elles sont liées au fragment HTML authentifié, ou à tout le document lorsque ses frontières ne peuvent être retrouvées. À la validation par le noyau, `MediaReferences` parcourt aussi les champs normalisés `url`, `href`, `rich` et les listes de médias connues, y compris les liens du pont `prime_block`. Les chemins sous `MediaConfig::urlPrefix()` sont rapprochés de `media.disk_path` par lots de 200, après déduplication et comparaison exacte ; les URL absolues doivent correspondre à l’origine HTTP(S) configurée du site. Les paramètres et fragments d’URL sont ignorés, mais les chemins traversants et les autres origines sont refusés. Pour les variantes d’image nommées par `ImageProcessor` (`-largeurxhauteur` et compagnons WebP), le résolveur cherche aussi les originaux possibles et ne retient leurs ID qu’après comparaison exacte avec les chemins dans `media.variants`. Si plusieurs originaux déclarent le même chemin, tous sont protégés ; si ce chemin est également un original, il l’est aussi. Le validateur reconstruit `data.items[].mediaId` à partir des fragments authentifiés et des fichiers ainsi trouvés, sans faire confiance à un index fourni par le client ni à un nom deviné. Ce format est reconnu par le suivi des médias du noyau pour les entrées et les zones ; la suppression ou la restauration d’un élément met l’index à jour lors d’une nouvelle sauvegarde ordinaire. La liste est dédupliquée, pas un décompte précis de chaque occurrence.

Ce contrat dépend de la forme actuellement reconnue par le noyau. Les documents Builder enregistrés avant ces améliorations ne sont pas réindexés avant leur prochaine sauvegarde ; les anciens fragments sans métadonnées ne peuvent pas être réindexés automatiquement par cette méthode. Les variantes aux noms non standards ou créées par une extension, URL sur d’autres domaines ou CDN, champs particuliers d’extensions, modèles de bibliothèque, copies de thème et révisions historiques ne sont pas tous suivis. La restauration d’une révision remet à jour les références de son contenu courant si les fichiers existent encore, mais une révision historique ne protège pas à elle seule ses fichiers contre la suppression. Les compteurs ne sont donc pas une preuve qu’un média peut être supprimé ; la suppression forcée reste possible dans le CMS.

La bordure responsive utilise trois propriétés indépendantes sur l’enveloppe du widget : `border_style` (`none`, `solid`, `dashed`, `dotted`, `double`), `border_width` (entier de 0 à 100 px) et `border_color` (hexadécimal ou référence de couleur du kit). Une valeur absente hérite du format supérieur ; `none` et `0` sont des réinitialisations explicites. Le sélecteur de style, l’épaisseur et la couleur s’appliquent aux quatre côtés ensemble, pas aux éléments internes ; le navigateur et le thème déterminent les valeurs initiales non définies. Le validateur et le compilateur refusent chacun les valeurs hors liste et aucun script public n’est ajouté. L’aperçu emploie les mêmes limites et valeurs ; comme pour les autres styles, la feuille compilée demeure requise pour le rendu public.

`box_shadow` est un choix responsive parmi `none`, `soft`, `medium` et `strong`, qui se développe en valeurs CSS fixes communes à l’aperçu et au compilateur. La valeur absente hérite ; `none` efface explicitement l’ombre du format supérieur. L’ombre s’applique à l’enveloppe du widget et aucun script public n’est requis. La personnalisation de couleur, de direction, d’étalement, de flou ou d’ombre interne n’est pas implémentée ; les valeurs CSS arbitraires sont refusées par le validateur et ignorées par le compilateur.

Le CSS public est compilé à partir d’une liste fermée, sans interpolation CSS libre. Pour `padding` et `margin`, les anciens raccourcis uniformes restent inchangés. Les nouvelles clés `padding_top/right/bottom/left` acceptent des longueurs positives ou nulles bornées à 2 000 ; `margin_top/right/bottom/left` acceptent en plus `auto` et des longueurs signées bornées à ±2 000. Les unités permises sont `px`, `%`, `em`, `rem`, `vw`, `vh`, ou un entier représentant des pixels. À chaque appareil, le raccourci est émis avant les quatre valeurs par côté, quel que soit l’ordre des clés du JSON ; le panneau, l’aperçu et le CSS public suivent la même cascade. Un raccourci tablette/mobile réinitialise les quatre côtés du format supérieur, puis chaque côté explicite du même format prime ; vider ce côté ou le raccourci rétablit la source précédente, y compris zéro. Une marge négative peut produire des chevauchements ; le résultat de `auto` dépend de la disposition du navigateur. Aucun script public n’est ajouté pour les espacements. La visibilité responsive accepte uniquement `show` ou `hide` dans les styles de chaque appareil ; une valeur absente hérite du format supérieur. Le compilateur émet `display:none!important` dans des plages exclusives aux points de rupture configurés : un `show` ultérieur ne modifie donc pas le type de disposition initial (`flex`, `grid`, bloc ou autre). Le masquage HTML de Structure et celui des ancêtres restent prioritaires. Les éléments masqués restent dans le HTML et réapparaissent si la feuille n’est plus chargée : ce n’est pas un contrôle d’accès. Le panneau et l’aperçu utilisent la même chaîne d’héritage ; l’éditeur normalise les tableaux vides renvoyés par PHP avant de modifier une carte de styles. La position responsive accepte `static`, `relative`, `absolute`, `fixed` et `sticky`. Ses quatre décalages signés sont bornés à ±2 000 (`px`, `%`, `em`, `rem`, `vw`, `vh`) et l’ordre de superposition entier à ±1 000 ; `auto` réinitialise explicitement chaque valeur héritée, contrairement à un champ vide. Le compilateur vérifie ces valeurs indépendamment du validateur et l’aperçu suit le même héritage. Les règles de flux, de défilement et de contexte d’empilement restent celles du navigateur et du thème ; en particulier un ordre négatif peut masquer un élément derrière un parent. Les instantanés publics sont conservés dans `storage/prime-builder/styles/` (ou le stockage configuré du CMS), vérifiés par empreinte et relus pour les anciennes URL. Les CSS d’aperçu privé ne sont pas archivés. La tâche `prime-builder.prune-styles` supprime les instantanés inutilisés depuis plus de 366 jours ; la désinstallation les retire. Si l’écriture échoue, la route actuelle répond sans cache immuable : prévoir stockage et planificateur opérationnels. Les anciennes URL créées avant l’ajout des instantanés ne peuvent pas être recréées si leurs données ont changé. Le serveur refuse les requêtes ultérieures pour une entrée devenue privée, mais une feuille déjà mise en cache publiquement dans un navigateur ou un CDN ne peut pas être révoquée avant son expiration.

Les scripts publics du plugin sont externes et chargés conditionnellement ; aucun script ou bloc `<style>` public n’est injecté par ce plugin. Le thème et le CMS ont leurs propres politiques CSP. L’éditeur applique des attributs de style dans l’iframe pour les modifications non enregistrées. Pour une modification d’un seul élément sans changement de structure, il transmet l’arbre entier pour validation mais ne demande et ne remplace que son sous-arbre ; les changements structurels ou concurrents déclenchent un rendu complet. Les réponses périmées sont ignorées et un élément manquant provoque une réconciliation complète. L’iframe est de même origine ; en l’absence de `.pb-layout`, l’aperçu remplace `.aurora-prose`, sinon le contenu de `main`, ce qui peut être inadapté à d’autres thèmes.

## Ajouter un widget tiers

Un autre plugin actif peut filtrer `prime_builder.widgets`. Exemple dans son `register(PluginContext $context)` (les clés de traduction appartiennent au plugin tiers) :

```php
use Prime\Security\HtmlSanitizer;

$context->hooks()->filter('prime_builder.widgets', static function (mixed $widgets): mixed {
    if (!is_array($widgets)) {
        return $widgets;
    }
    $widgets['acme_note'] = [
        'label' => 'plugin::acme.widgets.note',
        'category' => 'base', // structure, base ou pro
        'container' => false,
        'fields' => [
            'message' => ['type' => 'text', 'max' => 300, 'label' => 'plugin::acme.fields.message'],
        ],
        'render' => static function (array $settings, HtmlSanitizer $sanitizer): string {
            $message = is_string($settings['message'] ?? null) ? $settings['message'] : '';
            return '<p>' . htmlspecialchars($message, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') . '</p>';
        },
    ];
    return $widgets;
});
```

Parmi les types de champs reconnus figurent `text`, `multiline`, `rich`, `integer`, `enum`, `href`, `url`, `slug`, `media_list`, `price_items`, `testimonial_items`, `media_carousel_items`, `slideshow_items`, `portfolio_items`, `code` et `json_object`. `price_items` est un champ texte multiligne validé, limité à 30 lignes non vides `nom | prix | description facultative` ; ce sont des textes, pas des montants calculables. Un `enum` fournit une liste `values` et peut fournir des `option_labels` dont les valeurs sont des clés de traduction. Le rendu fourni par un callback est encore filtré par `sanitizeBasic` : le HTML interactif arbitraire n’est donc pas garanti. Le code PHP d’une extension est du code de confiance ; il ne constitue pas un bac à sable. Un `script` public éventuel doit être un chemin local `/assets/plugins/{slug}/...js`, sans `..` ; il est enregistré uniquement si le widget est présent. Les champs sont génériques : il n’y a pas encore d’API d’éditeur personnalisée complète pour les widgets.

## Vérifier dans une instance isolée

Les commandes suivantes supposent une copie du plugin dans un checkout **de test** de Prime CMS, avec ses dépendances de développement installées. Les tests E2E modifient et publient leur page : ne pas les lancer contre un site réel.

```bash
# Depuis le CMS de test
composer install --no-interaction --prefer-dist
# Par défaut, les tests utilisent la fixture SQLite du CMS.
vendor/bin/phpunit --bootstrap tests/bootstrap.php content/plugins/prime-builder/tests
# Pour exécuter les tests d’intégration sur une instance MySQL de test isolée,
# renseigner PRIME_TEST_DB_HOST, PRIME_TEST_DB_PORT, PRIME_TEST_DB_USERNAME
# et PRIME_TEST_DB_PASSWORD dans l’environnement :
PB_TEST_MYSQL=1 vendor/bin/phpunit --bootstrap tests/bootstrap.php content/plugins/prime-builder/tests
vendor/bin/phpstan analyse --configuration content/plugins/prime-builder/phpstan.neon --no-progress
vendor/bin/php-cs-fixer fix content/plugins/prime-builder --config .php-cs-fixer.dist.php --dry-run --diff --no-ansi
php bin/prime lang:check --strict

# Depuis le dépôt du plugin
npm test
# Mesure indicative sur la fixture SQLite du CMS (copie du plugin à jour requise)
php tools/benchmark.php /chemin/vers/prime-cms
cd tests/e2e
npm ci --no-audit --no-fund
npx playwright install --with-deps chromium
# Reproduire les fixtures et variables E2E_* de .github/workflows/ci.yml,
# dont E2E_FORM_ENTRY_ID (page vierge formulaire-test) et E2E_MENU_ENTRY_ID
# (page vierge pour le parcours clavier complet). Les tests publient et modifient
# ces pages et suppriment un envoi : ne jamais viser une installation réelle.
npm test
```

Avec `PB_TEST_MYSQL=1`, chaque fixture d’intégration crée puis supprime une base aléatoire `prime_builder_test_*` : le compte MySQL doit avoir les droits `CREATE DATABASE` et `DROP DATABASE`. Ne jamais pointer ces tests vers une instance contenant des données réelles. PHPStan niveau 8 analyse le code source, les vues, les langues, les tests, les outils et la configuration du fixer ; sa configuration utilise l’autoloader de développement du CMS installé par Composer. La CI clone le CMS, installe MySQL 8 et les dépendances de développement, crée des contenus de test, démarre le serveur, puis exécute ces contrôles. Le job navigateur installe le plugin à partir d’un ZIP via la CLI et vérifie ensuite la désactivation, la désinstallation et la conservation du contenu dans une instance jetable ; il ne teste pas le téléversement ZIP dans l’administration. Les résultats Playwright et le journal du serveur sont publiés comme artefact. Les scans axe sont limités aux violations sérieuses/critiques des écrans exercés : ils ne remplacent pas un audit WCAG manuel. Le `RETOUR.md` donne les résultats observés et les limites du prototype.
