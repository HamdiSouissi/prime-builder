# Migrations

La migration `2026_11_21_000001_create_prime_builder_form_tables.php` crée trois tables préfixées par le CMS :

- `prime_builder_submissions` : contenu, widget, nom, adresse e-mail, message et date UTC. L’adresse IP n’y est pas enregistrée ;
- `prime_builder_form_tokens` : empreintes des jetons déjà utilisés et leur expiration, séparées des messages pour empêcher un rejeu après suppression ;
- `prime_builder_form_limits` : compteurs temporaires par clé HMAC et expiration, sans IP en clair.

La migration `2026_11_21_000002_create_prime_builder_form_files.php` ajoute `prime_builder_form_files` : nom, type détecté, taille et, à l’origine, octets encodés en base64, liés à un envoi. Depuis `1.0.3`, les nouvelles pièces utilisent le stockage privé décrit plus bas et les anciennes migrent progressivement. Cette migration est déclenchée sur une installation active lors de la mise à niveau du plugin vers `0.1.1` et à l’activation d’une nouvelle installation.

La migration `2026_11_21_000003_create_prime_builder_form_notifications.php` ajoute `prime_builder_form_notifications` : référence à l’envoi, type, destinataire et identifiant de tâche du CMS. Le destinataire n’est pas dans le payload de la file, qui ne contient qu’un identifiant technique. Elle est appliquée à la mise à niveau vers `0.1.2` et à l’activation d’une nouvelle installation ; les messages et fichiers existants sont conservés. La version `1.0.0` n’ajoutait pas de migration : un remplacement ZIP réel depuis `0.1.2` a conservé ces données et les trois migrations sur deux installations de test, sans couvrir toutes les configurations.

La migration `2026_11_21_000004_prepare_theme_model_index.php`, introduite en `1.0.1`, crée uniquement un marqueur d’index dérivé. Au premier usage, le plugin construit le répertoire signé et les résultats de validation, en conservant la source et les champs supplémentaires des anciens modèles. Les modèles invalides restent inchangés et sont revalidés au rendu. La migration inverse retire le répertoire dérivé, pas les modèles ; sauvegarder le site avant une mise à niveau ou un retour arrière.

La migration `2026_11_21_000005_extend_prime_builder_submissions.php`, introduite en 1.0.2, ajoute les colonnes nullables `model_id` et `fields_json` sans modifier les envois existants. `model_id` identifie les nouveaux envois de modèle ; `fields_json` contient l’instantané structuré des nouveaux formulaires personnalisés. Les envois antérieurs et les formulaires fixes restent nuls sans interprétation rétrospective. La migration est relançable après une modification DDL partielle et ne supprime pas les colonnes à son retour arrière.

La migration `2026_11_21_000006_prepare_private_form_files.php`, introduite en 1.0.3, ajoute les colonnes `storage_key`, `content_sha256`, `migration_error`, un index et la table `prime_builder_form_file_gc`. Elle est relançable après une application DDL partielle ; elle ne déplace ni n’efface les anciens octets. Le plugin migre ensuite les pièces valides par petits lots, sous verrou : synchronisation du fichier, relecture et vérification, puis synchronisation des répertoires avant remplacement de la référence en base. Les valeurs invalides restent en base et sont signalées, sans bloquer les autres. Les suppressions sont inscrites en base avant leur collecte sur disque ; un balayage reprend aussi les fichiers non référencés après un délai. Le diagnostic compte les travaux en attente mais ne vérifie pas tous les fichiers référencés. Configurez et surveillez le planificateur, le stockage partagé non public et le verrouillage `flock`, et sauvegardez la base et le stockage de façon cohérente. Les permissions, les alias du serveur et la disponibilité de `fsync` sur les répertoires doivent être vérifiés sur le système cible.

Les remplacements ZIP réels 1.0.1 → 1.0.3 et 1.0.2 → 1.0.3 ont été vérifiés sur des CMS 1.0.1 et 1.0.2 jetables avec MySQL 5.7. Le retour arrière de la migration 006 supprime la table de collecte mais ne réécrit pas les pièces sur disque en base ; une version précédente ne peut donc pas nécessairement les lire. Pour revenir en arrière, restaurer une sauvegarde cohérente de la base, du stockage et d’`APP_KEY` créée avant la mise à jour.

Le gestionnaire de plugins du CMS exécute les migrations à l’activation et leurs méthodes `down()` à la désinstallation. **La désinstallation détruit tous les envois, pièces jointes, notifications et compteurs** ; sauvegarder et vérifier la restauration au préalable et interrompre le trafic public et les workers. Le CMS peut continuer après une erreur du hook : contrôler les journaux et le résultat, car la synchronisation n’est pas garantie dans ce cas. La désactivation seule conserve ces données. La tâche `prime-builder.purge-submissions` supprime les messages, leurs pièces jointes et notifications ainsi que les tâches associées lorsqu’ils dépassent la durée configurée (30 jours par défaut, de 1 à 3 650 jours) ; elle nettoie aussi les jetons et compteurs expirés. Le worker refuse de livrer une notification déjà expirée même si la purge n’a pas encore tourné. Un e-mail déjà transmis ne peut pas être rappelé ; les journaux, les fournisseurs et les sauvegardes restent hors de cette purge et doivent être gérés séparément.

Les instantanés de styles publics sont des fichiers sous le stockage privé du CMS ; le hook de désinstallation du plugin les supprime et la tâche `prime-builder.prune-styles` nettoie les fichiers anciens. Le CMS gère la suppression des réglages et capacités préfixés à la désinstallation. La vérification réelle du cycle de vie est exécutée sur une installation MySQL jetable par le workflow CI ; consulter `RETOUR.md` pour les résultats effectivement observés.
