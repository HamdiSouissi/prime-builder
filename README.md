# Prime Builder

Plugin de composition visuelle pour Prime CMS 1.0.1 et versions ultérieures compatibles. Il utilise le moteur de contenu et le thème actifs de Prime CMS, sans dépendance PHP ou JavaScript tierce à l’exécution.

> **État : prototype partiel, version 0.1.0.** Il ne constitue pas encore un remplacement complet d’un constructeur visuel professionnel. Le Theme Builder se limite aux en-têtes et pieds de page configurés par copies de modèles ; un formulaire de contact fixe existe, mais le constructeur de formulaires complet, les popups, les widgets globaux et de nombreuses fonctions demandées manquent. Ne l’utilisez pas en production sans revue, sauvegarde et tests adaptés à votre site. Voir [RETOUR.md](RETOUR.md).

## Prérequis

- Prime CMS ≥ 1.0.1 avec PHP 8.2–8.x et les extensions requises par le CMS. **Privilégiez Prime CMS 1.0.2 ou une version ultérieure corrigée.** Le noyau 1.0.1 peut laisser un jeton conserver les droits révoqués. Lorsque Prime Builder est actif sur 1.0.1, il enveloppe l’authentification HTTP de l’API et intersecte les droits du jeton avec ceux du compte avant l’autorisation, pour les routes du noyau comme du plugin. Cette protection ne corrige pas le noyau : elle disparaît si le plugin est désactivé, ne couvre pas les appels directs au service de jetons hors de la pile HTTP et peut être remplacée par une autre extension utilisant le même alias `api.auth`. Un avertissement figure dans le diagnostic système. La compatibilité des futures versions n’a pas été vérifiée ; voir [RETOUR.md](RETOUR.md) pour les tests observés.
- Accès à l’administration et aux capacités nécessaires : `prime_builder.edit` **et** les permissions de modification du contenu concerné. La publication requiert en outre la permission de publication du type de contenu. Les éditeurs peuvent consulter et insérer les modèles ; `prime_builder.templates` est requis pour enregistrer, importer ou supprimer. Le widget HTML filtré exige aussi `prime_builder.unfiltered_html` pour sa création, sa modification et son insertion depuis un modèle. La page de réglages nécessite `prime_builder.settings`. Les en-têtes et pieds de page du Theme Builder nécessitent `prime_builder.theme_builder` ; la consultation et la suppression des envois nécessitent `prime_builder.forms`.
- API REST du CMS activée pour enregistrer et actualiser les aperçus. Le dossier de stockage de Prime doit être accessible en écriture pour conserver les anciennes feuilles CSS à empreinte.
- Un navigateur moderne avec JavaScript pour l’éditeur et l’envoi du formulaire de contact. Le contenu statique enregistré reste lisible sans JavaScript ; les listes d’articles utilisent alors un lien de repli vers l’archive et le formulaire indique qu’il ne peut pas être envoyé.

## Installation

La racine de ce dépôt est le dossier du plugin : `plugin.json` doit se trouver directement dans `content/plugins/prime-builder/`. Choisir **une** des méthodes suivantes, puis activer le plugin. Prévoir une sauvegarde et utiliser une instance de test.

### 1. Copie du dossier

Copier les fichiers du dépôt dans `content/plugins/prime-builder/`, sans `.git`, `.arena` ni `node_modules`, puis, depuis le dossier du CMS :

```bash
php bin/prime plugin:activate prime-builder
```

Si nécessaire, `php bin/prime plugin:publish-assets prime-builder` republie les fichiers statiques. Cette méthode ne modifie pas le code du CMS.

### 2. Téléversement ZIP dans l’administration

Depuis un checkout Git du dépôt, produire une archive dont l’unique dossier racine est `prime-builder/` :

```bash
git archive --format=zip --prefix=prime-builder/ HEAD -o prime-builder.zip
```

Dans Prime CMS, ouvrir **Extensions**, téléverser l’archive par l’écran d’installation, puis activer Prime Builder. Le ZIP généré contient l’état committé, pas les modifications de travail non committées.

### 3. Installation ZIP en ligne de commande

Avec la même archive, depuis le dossier du CMS :

```bash
php bin/prime plugin:install /chemin/vers/prime-builder.zip
php bin/prime plugin:activate prime-builder
```

Le CMS installe le ZIP inactif. Voir son aide avant d’utiliser `--replace` ou `--force` pour remplacer une installation existante.

## Premiers pas

1. Dans **Prime Builder › Réglages**, vérifier les types activés. Les pages sont activées par défaut ; articles et autres types peuvent y être activés. Enregistrer d’abord tout nouveau contenu.
2. Ouvrir le contenu dans l’administration, puis **Modifier avec Prime Builder**. L’aperçu est une iframe de même origine utilisant le thème du site.
3. Ajouter des éléments depuis la recherche ou les catégories. Un conteneur sélectionné reçoit les nouveaux éléments. Dans le canevas ou **Structure**, glisser un élément avant/après un autre ou vers le centre d’un conteneur ; les repères corail montrent la destination. Au clavier, sélectionner l’élément et utiliser **Monter**, **Descendre** ou **Déplacer vers**. Dans Structure, les éléments peuvent aussi être renommés, repliés ou masqués ; le masquage est visuel, pas une protection de confidentialité (le HTML reste présent). Le menu **Actions de l’élément** (ou clic droit) propose copie, collage, collage ou réinitialisation du style, duplication et suppression ; la copie reste en mémoire dans l’éditeur ouvert. Les onglets **Contenu**, **Style** et **Avancé** exposent les réglages disponibles. L’**Historique** permet de revenir à une action depuis l’ouverture ou la dernière sauvegarde ; il ne comprend pas les changements de statut ou de planification.
4. Choisir ordinateur, tablette ou mobile pour ajuster les valeurs de style disponibles. Dans **Avancé**, la visibilité peut être héritée, affichée ou masquée pour chaque format. Un parent masqué reste masqué même si son enfant est réglé sur « Afficher » ; le bouton de masquage de **Structure** reste indépendant. Ce masquage est purement visuel : le HTML reste public et peut réapparaître si la feuille CSS est indisponible ou le plugin désactivé. Ne l’utilisez jamais pour des données privées. La position (normale, relative, absolue, fixe ou collante), les quatre décalages et l’ordre de superposition peuvent aussi varier par format. Vider un nombre rétablit l’héritage ; choisir **Automatique** réinitialise explicitement un décalage ou un ordre hérité. Les valeurs négatives peuvent faire sortir un élément de l’écran ou le placer derrière un parent ; une position collante dépend du défilement et de ses conteneurs. Vérifiez le résultat et l’accès au clavier sur chaque format. Les valeurs absentes héritent des tailles supérieures ; le panneau indique la valeur et le mode dont elles héritent. Les points de rupture et le petit kit global de couleurs/taille se règlent dans le CMS.
5. Choisir brouillon, publié ou planifié (date saisie en UTC), puis **Enregistrer**. L’historique local annuler/rétablir est distinct des révisions du CMS, accessibles par le lien de révisions. Le CMS doit avoir son planificateur opérationnel pour les publications programmées.

Raccourcis : `Ctrl/⌘ S` enregistrer, `Ctrl/⌘ K` ouvrir les commandes, `Ctrl/⌘ Z` annuler et `Ctrl/⌘ Y` ou `Ctrl/⌘ Maj Z` rétablir hors des champs de texte. Les modifications non enregistrées déclenchent un avertissement ; une copie locale par utilisateur et contenu peut être proposée à la réouverture. Ce stockage navigateur n’est pas une sauvegarde serveur.

**Attention à la conversion :** à l’ouverture, le constructeur tente de convertir les blocs Prime existants dans leur ordre, sans écrire avant l’enregistrement. Les blocs pris en charge deviennent des blocs Prime éditables si leur rendu est identique au fragment attribué ; les autres sont conservés en lecture seule. Pour un seul bloc dont le moteur n’est plus disponible, le fragment est déduit si les rendus actuels des autres blocs correspondent au début et à la fin du HTML sauvegardé. Cela suppose que ces rendus n’ont pas changé depuis la sauvegarde : le CMS ne conserve pas les limites de chaque fragment. Si elles ne peuvent être retrouvées, tout le HTML sauvegardé est regroupé dans un élément en lecture seule : on peut déplacer ou supprimer cet élément entier, mais pas ses blocs séparément. À l’enregistrement, les réglages originaux de ces blocs ne sont pas conservés et leur contenu dynamique reste figé. L’éditeur affiche cet avertissement à chaque ouverture. Les ancres des titres reconvertis individuellement sont conservées. Les limites de document et une clé `APP_KEY` valide restent obligatoires ; le chiffrement augmente la taille et peut empêcher la conversion. Les fragments sont liés à leur contenu et à la clé du site. Sauvegardez et vérifiez le résultat avant tout enregistrement.

## Éléments et modèles disponibles

Les 63 éléments sélectionnables comprennent : conteneur, titre, texte, image, bouton, séparateur, espace, citation, alerte, progression, ancre, liste, accordéon, carte éditoriale, boîte à icône, icône, liste d’icônes, boîte image, témoignage, carrousel de témoignages, carrousel de médias, diaporama, portfolio, avis, boîte retournable, titre animé, code coloré, appel à l’action, table de prix, liste de prix, compte à rebours, formulaire de recherche, menu de navigation, fil d’Ariane, titre et logo du site, boutons de partage, sommaire automatique, bascule, réseaux sociaux, zone du thème, carte OpenStreetMap, note par étoiles, compteur, galerie, carrousel d’images, vidéo, audio, grille d’articles, contenu actuel, titre, extrait, contenu, image à la une, informations, navigation et boîte auteur du contenu courant, titre et liste d’archive, formulaire de contact fixe, bloc Prime, HTML filtré et onglets. Le widget HTML est réservé à une capacité dédiée. Certains médias locaux peuvent être choisis avec le sélecteur du CMS ; la vidéo accepte une piste WebVTT et une transcription. Les onglets restent lisibles sans JavaScript.

- **Contenu courant** : widgets distincts pour le titre, l’extrait, l’image à la une et les informations (date, auteur et catégories publiques). Le titre et son lien, la longueur de l’extrait, la taille de l’image et les informations visibles sont configurables. Les valeurs viennent du CMS et sont actualisées après chargement si JavaScript et l’API sont disponibles. Le HTML enregistré sans JavaScript peut conserver d’anciennes valeurs ; lors d’une publication depuis un brouillon, les widgets peuvent être vides dans ce repli pour ne pas exposer les anciennes données privées. Les catégories et le nom de l’auteur n’y sont jamais enregistrés : ils ne s’affichent qu’après vérification du caractère public de la taxonomie et de l’activité du compte.
- **Navigation et auteur du contenu** : liens vers les contenus publiés voisins du même type et boîte auteur avec avatar, biographie et lien d’archive facultatifs. La navigation évite les pages dont un parent est privé ; la boîte masque les comptes inactifs. Dans le contenu d’une entrée, ces deux widgets restent vides sans JavaScript ou si l’API est indisponible afin de ne pas conserver des données susceptibles de devenir privées. Aurora affiche déjà sa propre boîte auteur et sa navigation sur les articles : les ajouter peut créer des doublons.
- **Widgets de contenu dans une partie de thème** : les six widgets ci-dessus peuvent aussi être placés dans l’en-tête ou le pied de page lorsque le thème appelle `site.partial`. Ils utilisent alors l’entrée publique du contexte et sont rendus côté serveur, y compris les catégories publiques, les voisins et l’auteur, sans JavaScript. Ils restent vides hors contexte compatible ou si l’entrée ou ses ancêtres ne sont pas publics. Pour préserver la fraîcheur des données, le cache de pages du CMS est contourné pour tout le site tant qu’une partie active contient l’un de ces widgets.
- **Contenu de l’entrée** : dans une partie de thème, ce widget copie le contenu public renvoyé par le CMS, y compris ses blocs dynamiques. Il reste vide sur les archives, recherches, entrées privées et dans l’entrée elle-même pour éviter la récursion. Le thème peut déjà afficher ce contenu : l’ajout de ce widget le duplique, et les modèles dédiés au contenu seul restent à construire. Les identifiants courants, leurs références, les liens de fragment et les zones actualisées sont isolés entre copies ; les widgets Builder testés conservent leurs scripts et styles déclarés. La copie **n’est pas une reproduction universelle** : ses balises `script` sont retirées, des scripts tiers ou règles CSS dépendant d’anciens ID peuvent cesser de fonctionner, et l’analyse HTML de libxml peut modifier certains contenus modernes ou mal formés. Un fragment de plus de 2 Mio ou sortant de son enveloppe n’est pas copié. Vérifiez les extensions et médias employés sur votre site ; la page originale n’est pas modifiée.
- **Titre et liste d’archive** : ces widgets utilisent la liste et la pagination déjà résolues par le CMS pour l’accueil affichant les articles récents, le blog, une archive de type, de terme ou d’auteur et la recherche. Le titre et la liste (cartes ou liste, extrait et pagination facultatifs) sont rendus côté serveur, utilisables sans JavaScript ; les brouillons, publications futures et pages aux parents non publics sont exclus. La pagination suit le nombre de résultats fixé dans les réglages de lecture du CMS. Les widgets n’ont pas de contexte d’archive dans le contenu d’une page : ils y restent vides sur le site et affichent une explication dans l’éditeur. Ils peuvent être utilisés dans les parties d’en-tête et de pied de page si le thème appelle `site.partial` ; sur une entrée ou une page d’accueil statique ils restent vides. Les modèles dédiés aux archives ne sont pas encore implémentés. Aurora affiche déjà ses propres résultats : une partie de thème qui ajoute ces widgets peut donc les dupliquer. Le cache de pages du CMS est contourné tant qu’une partie de thème contient l’un des deux widgets, pour éviter des résultats périmés ; une liste peut contenir moins d’éléments que le total si des pages non accessibles sont écartées.

- **Appel à l’action** : titre, texte, image et lien facultatifs. **Table de prix** : prix et période en texte, avantages et lien facultatif. **Liste de prix** : jusqu’à 30 lignes `nom | prix | description facultative` ; les lignes vides sont ignorées. Les prix sont des textes d’affichage, sans calcul ni paiement.
- **Compte à rebours** : titre, niveau de titre, échéance saisie en UTC à la minute et message de fin personnalisable. Le décompte utilise l’horloge du visiteur et peut donc être erroné si elle est mal réglée ; il ne doit pas servir à contrôler une vente ou un accès. Sans JavaScript, seule l’échéance UTC enregistrée reste visible, même après son passage ; l’aperçu de l’éditeur présente ce repli statique.
- **Carrousel de témoignages** : jusqu’à 20 lignes `texte | auteur | fonction | URL du portrait`, les trois derniers champs étant facultatifs. Le caractère `|` sépare les champs et ne peut pas figurer dans leur contenu. Sans JavaScript, toutes les citations restent visibles ; sinon, les commandes clavier permettent de changer de témoignage, sans défilement automatique. Un portrait hébergé par un tiers peut lui transmettre l’adresse IP du visiteur.
- **Carrousel de médias** : jusqu’à 20 lignes saisies manuellement, `image | URL | texte alternatif | légende` ou `video | URL du fichier | titre | URL WebVTT | transcription`. La légende, la piste de sous-titres et la transcription sont facultatives ; le titre vidéo est obligatoire. Utilisez un texte alternatif vide seulement pour une image décorative, et fournissez sous-titres et transcription lorsque nécessaires. Le séparateur `|` ne peut pas figurer dans les champs. Choisissez la langue commune des sous-titres (français ou anglais). Sans JavaScript, toutes les diapositives restent visibles ; sinon les boutons et les flèches les parcourent sans rotation automatique, et une vidéo est mise en pause lorsqu’elle est masquée. Seuls les fichiers vidéo compatibles avec le navigateur sont pris en charge ici, pas les pages YouTube ou Vimeo. Utilisez de préférence des URL du site : la politique de sécurité par défaut du CMS bloque les images, vidéos et sous-titres distants ; si elle est modifiée pour les autoriser, un fournisseur tiers peut recevoir l’adresse IP du visiteur. Les sous-titres distants nécessitent aussi une configuration CORS compatible. Les dimensions d’image ne sont pas encore configurables pour ce widget.
- **Diaporama** : jusqu’à 20 lignes `URL image | texte alternatif | titre | description | libellé du lien | URL du lien`. Le titre et la description sont facultatifs ; le libellé et l’URL du lien doivent être fournis ensemble. Un texte alternatif vide est réservé aux images décoratives. Le séparateur `|` ne peut pas figurer dans les champs. Les images sont recadrées au format 16:9 et leurs dimensions ne sont pas configurables ; la carte de texte est superposée sur grand écran et placée sous l’image sur mobile. Sans JavaScript, toutes les diapositives restent visibles ; sinon les commandes et les flèches permettent de naviguer sans rotation automatique. La CSP du CMS bloque par défaut les images distantes.
- **Portfolio** : jusqu’à 24 projets saisis manuellement, une ligne `URL image | texte alternatif | titre | catégorie | description | URL du projet`. Titre et catégorie sont obligatoires ; description et URL sont facultatives. Une seule catégorie par projet, 12 catégories au maximum ; le caractère `|` est réservé comme séparateur. Les images sont recadrées en 4:3, sans dimensions individuelles configurables. Le filtre à boutons est utilisable au clavier ; sans JavaScript tous les projets restent visibles. Il ne s’agit pas d’une requête automatique sur les contenus du CMS ; la CSP du CMS bloque par défaut les images distantes.
- **Avis** : une carte éditoriale avec titre, note entière de 0 à 5, texte, auteur, fonction et portrait facultatif. Les avis sont saisis manuellement ; le plugin n’en vérifie ni l’origine ni l’authenticité et ne calcule pas de moyenne. **Boîte retournable** : recto, verso et lien facultatif, avec bouton utilisable au clavier et animation réduite selon les préférences du visiteur. Sans JavaScript ou dans l’aperçu statique, les deux faces restent lisibles.
- **Titre animé** : titre en trois parties avec soulignement ou léger mouvement, joué une fois et désactivé si le visiteur préfère réduire les animations. **Code coloré** : source échappée avec coloration légère pour HTML, CSS, JavaScript, JSON et PHP, ou texte brut. Ce n’est pas un analyseur syntaxique complet ; au-delà de 1 000 unités colorées, le reste demeure du texte brut. Les longues lignes défilent au clavier. Ces deux widgets ne nécessitent pas JavaScript.
- **Formulaire de recherche** : libellé, texte indicatif et bouton personnalisables ; il soumet une recherche GET au moteur du CMS. Dans une entrée, le HTML enregistré reste utilisable sans JavaScript tant que l’adresse de recherche n’a pas changé. Avec JavaScript, l’adresse est actualisée sans effacer la saisie ; si l’API est indisponible, l’adresse enregistrée peut être ancienne. Dans les parties de thème, le formulaire est rendu par le serveur avec l’adresse actuelle, sans script propre ; les champs de l’en-tête, du pied et de la page ont des identifiants distincts. Une modification du réglage de recherche purge le cache de pages du CMS.
- **Menu de navigation** : sélection d’un menu du CMS et libellé accessible personnalisable. Les sous-menus utilisent des boutons natifs, et sur mobile le menu s’ouvre au clavier ; Échap referme le niveau courant et rend le focus. Dans une entrée, le HTML enregistré ne conserve pas de copie du menu : les liens sont actualisés par JavaScript et, sans JavaScript ou si l’API échoue, seul le lien d’accueil reste disponible. Dans l’en-tête ou le pied construits, le menu est calculé par le serveur et tous ses liens restent accessibles sans JavaScript ; avec JavaScript, les boutons de divulgation sont activés. Les destinations de type contenu, terme ou archive sont revérifiées ; les pages sous un parent privé ou inaccessible sont omises. Les URL saisies manuellement restent sous la responsabilité de la personne qui crée le menu. Le cache de pages du CMS est contourné sur tout le site tant qu’une partie contient ce widget, car les modifications de menu ne déclenchent pas toutes une purge. Les caches externes ne sont pas contrôlés. Le menu utilise le point de rupture mobile défini dans les réglages du constructeur (767 px par défaut), borné sous le point tablette.
- **Fil d’Ariane** : le fil fourni par le CMS est complété par les parents publics d’une page, avec un nom accessible personnalisable. Dans le contenu d’une entrée, JavaScript l’actualise depuis l’API ; sans JavaScript ou si l’API échoue, seul le lien d’accueil reste disponible. Dans une partie de thème, il est rendu côté serveur sans JavaScript pour l’entrée, le blog, les archives de type, de terme ou d’auteur et la recherche ; il est vide sur l’accueil et les contextes non pris en charge. Un parent privé, manquant, cyclique ou au-delà des 11 ancêtres admis rend le fil vide. L’API live du constructeur ne donne pas accès anonymement aux données d’une page publiée dont un parent n’est pas public. Cette protection ne modifie pas l’API de lecture du CMS, qui peut exposer une entrée publiée par son identifiant même si un parent est privé : ne comptez pas sur le statut du parent pour protéger un enfant sensible. Le cache de pages du CMS est contourné tant qu’une partie contient ce widget. Les routes personnalisées ne sont pas résolues par le fil dans une entrée et les libellés fournis par le noyau sont actuellement en français.
- **Boutons de partage** : Facebook, LinkedIn, X et e-mail peuvent être affichés ou masqués, avec un texte et un nom accessible personnalisables. Ce sont des liens ordinaires, sans SDK ni contact avec les réseaux avant activation ; le référent n’est pas transmis. Dans une entrée, JavaScript actualise l’adresse de la page en excluant les paramètres et le fragment, sans utiliser une éventuelle canonique SEO personnalisée. Dans les aperçus d’entrée, le lien vise l’adresse publique prévue, qui peut être inaccessible pour un brouillon. Sans JavaScript, les liens enregistrés peuvent devenir périmés après un changement d’adresse ; une URL de site absolue valide doit être configurée. Dans une partie de thème, les liens sont calculés côté serveur à partir de la canonique du CMS, y compris la canonique SEO d’une entrée, sans paramètres ni fragment et sans script propre. Ils sont indisponibles en aperçu, sur une erreur et dans les contextes non pris en charge. Le cache de pages du CMS est contourné sur tout le site tant qu’une partie contient ce widget ; les caches externes ne sont pas contrôlés.
- **Sommaire automatique** : liste hiérarchique des widgets Titre, Titre animé et blocs Prime de type titre du même document, même imbriqués, avec plage de niveaux et libellé configurables. Les éléments masqués sont exclus et les liens fonctionnent au clavier sans JavaScript. Cette première version ne recense pas les titres d’autres widgets, du thème, du HTML libre ou des contenus actualisés ; les ancres propres aux widgets évitent les collisions avec les ancres Builder connues, pas nécessairement celles du HTML libre ou du thème.
- **Carte OpenStreetMap** : le visiteur active la carte avant tout chargement du fournisseur ; un lien et l’attribution restent visibles sans JavaScript. Après activation, OpenStreetMap peut recevoir son adresse IP. La lecture réelle du fournisseur n’a pas été vérifiée dans la CI, où il est simulé.
- **Zone du thème** : sélection parmi les zones déclarées du thème actif et actualisation par l’API ; sans JavaScript, seul un message explicatif est affiché. Les ressources des widgets Builder imbriqués ne sont pas encore prises en charge et cette zone ne peut pas être placée dans les parties de thème du constructeur.
- **Grille d’articles** : choix d’un type public, d’une taxonomie publique rattachée au type et de 10 identifiants de termes au plus (séparés par des virgules, au moins un terme doit correspondre), d’un identifiant d’auteur, du tri, de 1 à 12 résultats, de la pagination et d’une liste ou de cartes à 1–4 colonnes. Les identifiants de termes peuvent être consultés dans `/api/v1/terms/category` ou `/api/v1/terms/tag` ; les identifiants d’auteur figurent dans l’administration ou l’API du CMS selon les droits. Les descendants d’un terme ne sont pas inclus automatiquement. Les brouillons, contenus privés et publications futures sont exclus ; les pages dont un ancêtre n’est pas publiquement accessible sont omises. La pagination est limitée à 1 000 pages. Avec JavaScript, les résultats sont actualisés par l’API sans mettre les titres en cache dans la page. Sans JavaScript ou si l’API est indisponible, seul un lien générique vers l’archive du type est conservé (vers la recherche pour les pages) : il ne reproduit ni les filtres ni la pagination et son adresse enregistrée peut devenir obsolète après un changement de permaliens. Le widget est exclu des parties de thème.
- **Contenu actuel** affiche titre, extrait, auteur ou date. La valeur sauvegardée peut être ancienne si JavaScript ou l’API est indisponible.
- **Bloc Prime** accepte un objet JSON pour l’un des huit types statiques autorisés : paragraphe, titre, liste, citation, code, séparateur, tableau ou encadré. Le bloc HTML libre du noyau, les blocs dynamiques et les autres types ne sont pas pris en charge par ce pont.
- **HTML filtré** utilise le profil `sanitizeBasic` du CMS : scripts, styles, iframes, attributs événementiels et URL dangereuses ne sont pas autorisés, même avec la capacité `prime_builder.unfiltered_html`. Le texte riche ordinaire utilise le même filtre ; la capacité distingue l’utilisation de ce widget, pas toute écriture de balises HTML filtrées. Un widget existant reste déplaçable ou supprimable après retrait de la capacité, mais son code devient non modifiable. Une `APP_KEY` valide est nécessaire pour signer son contenu et son entrée ; changer cette clé invalide les signatures. Les modèles partagés sont signés à nouveau lors de leur insertion par une personne autorisée.

  **Limite des opérations du noyau :** lorsqu’un appel direct au service ou à l’API de contenu tente de rejouer du HTML signé sans la capacité, le noyau peut répondre succès tout en conservant l’ancien contenu (d’autres champs, comme le titre, peuvent être enregistrés). L’API Prime Builder retourne 403 pour ces modifications. Une duplication ou création par le noyau convertit les widgets HTML en widgets texte riche afin de préserver leur contenu filtré, car l’identifiant du nouveau contenu n’existe pas encore. Vérifiez le résultat et utilisez l’éditeur Prime Builder pour modifier ce widget.
- La bibliothèque contient six sections et trois pages livrées. Depuis le menu contextuel d’un élément, une personne ayant `prime_builder.templates` peut enregistrer sa composition comme modèle partagé, puis l’insérer ou la supprimer dans la bibliothèque. Les fragments « Contenu d’origine » liés à une entrée ne peuvent pas être enregistrés comme modèles ; un modèle inséré est une copie indépendante, pas un widget global synchronisé. Les modèles de contact ne sont que des compositions statiques : ils ne fournissent **aucun formulaire fonctionnel**. Les compositions s’importent et s’exportent en JSON ; les URL d’images ne sont pas embarquées dans l’export.

## En-tête et pied de page du thème (fonction partielle)

Une personne ayant `prime_builder.theme_builder` peut ouvrir **Theme Builder — en-tête et pied de page**, choisir un modèle partagé enregistré dans le constructeur pour chaque partie et exclure jusqu’à 100 contenus par leur identifiant. Le thème actif doit appeler `$site->partial('header')` et `$site->partial('footer')` ; un thème qui inclut directement ses fichiers ne peut pas être remplacé par ce mécanisme. Un filtre précédent ayant déjà fourni une partie reste prioritaire. Sur un contenu exclu, le thème fournit ses parties habituelles.

La sélection enregistre une **copie statique** du modèle : sa suppression ultérieure dans la bibliothèque ne modifie pas le thème. Pour changer cette copie, enregistrer et sélectionner un nouveau modèle. Un modèle contenant le widget HTML filtré exige également `prime_builder.unfiltered_html` lors de la sauvegarde de la configuration ; le HTML reste filtré. Les widgets de liste d’articles, de contenu actuel, de zone du thème et de formulaire de contact ne sont pas acceptés directement dans ces parties statiques. Les widgets de contenu courant, le titre et le logo du site, le fil d’Ariane, le menu de navigation, les boutons de partage, le formulaire de recherche et les deux widgets d’archive y sont acceptés et rendus par le serveur ; le widget de contenu peut toutefois copier une entrée contenant des éléments autrement exclus. Les identifiants et ancres de widgets sont renommés pour les distinguer du contenu de la page ; les liens des widgets bouton et carte vers ces ancres sont adaptés, mais les liens saisis à l’intérieur du texte riche ne sont pas réécrits. Les conditions par type, terme et priorité, ainsi que les modèles de contenu, archive, recherche et 404 restent à construire. La modification de cette configuration déclenche la purge du cache de pages ; tester le site et la désactivation sur une copie.

## Formulaire de contact simple

Dans une page publique, ajouter **Formulaire de contact**, régler si besoin son titre et le texte du bouton, puis publier. Le formulaire comporte trois champs obligatoires fixes : nom, adresse e-mail et message. Les compositions de contact livrées dans la bibliothèque restent des exemples statiques : elles ne deviennent pas automatiquement des formulaires.

Avec JavaScript, le navigateur obtient un jeton temporaire sans cookie ; aucun jeton n’est inscrit dans le HTML mis en cache. La vérification côté serveur associe le jeton au contenu, au widget et à l’adresse réseau, impose un délai minimal et un usage unique ; pot de miel et quotas complètent cette protection, sans garantir l’absence de spam. Une `APP_KEY` valide et une API disponible sont nécessaires. Sans JavaScript ou après désactivation du plugin, l’envoi ne fonctionne pas.

Les messages sont enregistrés en base, **sans envoi d’e-mail**, et visibles dans **Envois de formulaires** uniquement avec `prime_builder.forms`. L’écran présente les 100 derniers et permet leur suppression ; il ne fournit ni recherche ni export. Une tâche planifiée supprime les messages de plus de 30 jours si le planificateur du CMS fonctionne ; la désinstallation supprime les tables et tous les messages. Les visiteurs doivent être informés du traitement de leurs données et l’opérateur doit prévoir ses sauvegardes, contrôles d’accès et obligations légales. Aucun fichier ne peut être téléversé ; champs personnalisés, étapes multiples et notifications par e-mail restent à construire.

## Désactivation et désinstallation

```bash
php bin/prime plugin:deactivate prime-builder
# Facultatif et destructif pour les envois, réglages, capacités et fichiers du plugin :
php bin/prime plugin:uninstall prime-builder
```

Le HTML rendu est enregistré dans les contenus par le CMS et sert normalement de repli lorsque le plugin est désactivé ; l’apparence, les onglets interactifs et l’actualisation des données ne sont alors plus garantis. Prime CMS 1.0.1 identifie les blocs dynamiques par leur type, sans modification du JSON par le plugin. Testez la désactivation sur une copie du site. La désinstallation retire également les tables et messages du formulaire, les instantanés CSS du plugin, ses réglages et capacités ; elle ne supprime pas les contenus enregistrés.
